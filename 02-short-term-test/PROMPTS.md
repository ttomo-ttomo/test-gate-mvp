# Claude Code向け短期テスト実施プロンプト（工程別）

> [WORKFLOW.md](WORKFLOW.md) に対応する5つの短い指示。**一括投入しない。1工程ずつ実行し、実測結果と人間の判断を確認してから次へ進む。** 既存の [CLAUDE_PROMPTS.md](../03-analyzer/CLAUDE_PROMPTS.md) はAnalyzer/Gate専用であり、本書とは別。

## 共通ルール（各工程の前提）

- 正規仕様/採択Issue/ADRを根拠とする。実装・既存テストの挙動を仕様として扱わない。
- AIは候補の整理・コード変更を支援するが、仕様の補完・期待値の承認・最終判断をしない。未決はOPEN_QUESTIONS.mdへ。TEST_RULES.mdを無断でapprovedにしない。
- まず既存ツールを調査する。利用不可のコマンド・カバレッジ値・テスト結果を捏造しない。新たな基盤/CI/外部LLMは原則導入しない。
- 検査・実測値はプログラム/実行ログから採る。実行不能・失敗・未実施を分けて記録する。
- 各回、対象外の変更はしない。最後に変更ファイル、実行コマンド、結果、未決事項、未実施範囲を簡潔に報告する。

## Prompt A — 簡易リスク評価（調査のみ）

```text
WORKFLOW.mdの「工程1」を読んでください。今回は調査だけです。
仕様・採択Issue・対象コードを確認し、重大な故障候補を最大5件、
影響度（高/中/低）、不確実性、根拠リンク、対応する受入条件のMarkdown表に整理してください。
受入条件にない重大な故障候補も見落とさないようにしてください。
最初に検証する1機能と受入条件を提案し、人間が選ぶまで確定しないでください。
仕様不明はOPEN_QUESTIONS.mdへの追記案として提示してください。
本番コード・テスト・TEST_RULES.mdは変更しないでください。

最後に、候補表、推奨する対象、未確認資料、人間が決める点を報告してください。
```

**次へ:** 人間が対象機能・受入条件を確定。

## Prompt B — 受入条件からテスト生成・実行

```text
WORKFLOW.mdの「工程2」を読んでください。人間が選んだ1機能のみ対象です。
SPEC_INDEX.mdで正規仕様、実装、既存テストの対応を確認してください。
CLAUDE_PROMPTS.mdのPrompt 1・2に沿って根拠付きのTEST_RULES.md行をpendingで提案・追加し、
不明点をOPEN_QUESTIONS.mdに記録してください。
承認が必要な行がある場合は、そこで止めて人間の確認事項を報告してください。
人間がapprovedにした後、check.py --strictで根拠を点検し、対象行のHOLDを確認してください。
承認済み期待値のみ使い、既存テストランナーで最小の実行可能なテストを作成・実行してください。
仕様にない期待値を作らず、テスト失敗を隠すためのassert変更はしないでください。

最後に、受入条件IDとテストの対応、実コマンド、PASS/FAIL/SKIP、ログ、
未決事項、未実施範囲を報告してください。
```

**次へ:** 人間の期待値承認と、最低1件のテスト実行結果がある。

## Prompt C — 分岐カバレッジ

```text
WORKFLOW.mdの「工程3」を読んでください。工程Bの対象機能だけを調べます。
既存環境で分岐カバレッジが計測できるか調査し、できれば実行してください。
行カバレッジと分岐カバレッジを区別し、対象・除外・ツール・コマンドを記録してください。
未実行の分岐を列挙し、仕様に照らして追加テスト候補を提案してください。
仕様が不明なら判断せず未決にしてください。追加テストの期待値は無断で確定しないでください。
計測できない場合は「未計測」と理由を報告してください。

最後に実測率（あれば）、未実行分岐、ログ、追加候補、未計測範囲を報告してください。
```

**次へ:** 計測結果または未計測理由と、優先分岐の扱いが明確。

## Prompt D — ミューテーション

```text
WORKFLOW.mdの「工程4」を読んでください。
対象機能で少数の変更（条件反転・境界変更など）を選び、実行方法を先に示してください。
既存ツールがあれば優先し、変更は1件ずつ隔離して実施してください。
各変更について元テストの成立、検出/生存/実行不能/等価疑いを
実行ログに基づき分類してください。ビルド失敗を無条件で検出成功にしないでください。
承認済み仕様・期待値は変更しないでください。
すべての変更を復元し、差分とベースラインのテスト結果を確認してください。

最後に変更ごとの結果表、実コマンド、未実施理由、復元確認を報告してください。
```

**次へ:** 全変更の復元が確認でき、実測結果が残っている。

## Prompt E — 欠陥注入

```text
WORKFLOW.mdの「工程5」を読んでください。
簡易リスク評価で人間が優先した故障から1〜2件を候補にしてください。
ローカル/隔離テスト環境のみを使い、本番・実ユーザーデータ・第三者環境は触らないでください。
先に故障の入れ方、検出を期待するテスト、観測点、復元方法を示してください。
実行条件が確認できない場合は注入せず、未実施理由を報告してください。
許可された範囲でベースライン → 1件注入 → テスト実行 → 結果記録
→ 復元 → ベースライン再確認を行ってください。
検出したかどうかはテスト実測結果で判断し、AIの印象で合格扱いしないでください。

最後に故障ごとの検出/非検出/未実施、ログ、課題、復元確認を報告してください。
```

**完了:** 実測結果・未検証範囲・復元状況が明示される。出荷可否は宣言しない。

## 工程間の引き継ぎ

別セッションへ移る場合は、直前のコミットSHA（あれば）、対象機能・受入条件ID、仕様の正本、承認待ちID、実行ログの場所、次の工程だけを渡す。長いチャット全文を毎回貼らない。
