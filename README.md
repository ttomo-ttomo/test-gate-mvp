# Test Gate MVP — Markdown表 + 決定的なAnalyzer/Gate

> **対象:** 新プロジェクトにコピー可能な最小構成。人間が編集するのはMarkdown表、判定するのはPython標準ライブラリ。AIは情報の探索とルール候補の作成を補助するが、毎回の合否を判断しない。

## なぜ作ったか

AIでテストを生成・実行できても、期待値が正しい仕様に基づくとは限らない。そこで「仕様とコードの食い違いを機械的に点検するAnalyzer」と「人間が承認した期待値の出典・未決事項を機械的に確認するGate」を、最小のファイル数で運用する。

**注意:** このMVPが判定するのは、仕様アンカーの存在、仕様ファイルの改訂、実装アンカーの存在、承認状態、未決事項である。コードの実行経路や仕様と期待値の意味的な同値性は証明できない。根拠の意味的な支持関係は人間が承認する。

## テスト計画の全体像と今回の検証範囲

機能単位のテストを実施するタイミングで使う。テスト計画全体のうち、このMVPが扱うのは△の2項目だけである。

| 今回実施 | 項目 | 目的 |
| --- | --- | --- |
| — | リスク評価 | 重要な故障に優先順位を付ける |
| — | 完了基準と判断者 | 出荷可否を判断する |
| — | 仕様の穴を先に潰す | 未規定の条件を人間が決定する |
| △ | 仕様と実装の整合性確認 | 仕様と現在のコードの食い違いを発見する |
| △ | テスト期待値の根拠確認 | 仕様にない期待値をテストへ混入させない |
| ○ | 受入条件からのテスト生成 | 受入条件を実行可能なテストにする |
| — | 環境・構成 | 本番相当の経路で確認する |
| — | 非機能 | 負荷・セキュリティ・コストを確認する |
| ○ | 分岐カバレッジ | 未実行箇所を発見する |
| ○ | ミューテーション | テストがコード変更を検出するか確認 |
| ○ | 欠陥注入 | 想定する故障の検出を確認 |
| — | 運用 | CI・監視・保守を検討する |

○＝元の実験で実施、△＝今回のMVPで限定的に取り扱う、—＝MVPの対象外。

**△の2項目は、仕様全体の正しさを検証する仕組みではない。** AIが扱う根拠の品質を改善する小さな補助工程である。

### 責任分担

| 作業 | AI | 人間 | プログラム |
| --- | --- | --- | --- |
| 仕様・Issueの探索 | ○ | | |
| ルール候補の作成 | ○ | | |
| 仕様の正本決定 | | ○ | |
| 未決事項の決定 | | ○ | |
| 期待値と根拠の承認 | | ○ | |
| 根拠の変更検出 | | | ○ |
| 実装アンカーの存在確認 | | | ○ |
| Gate判定 | | | ○ |
| 判定の再現性確認 | | | ○ |

`ALLOW` でも、プログラムが仕様の意味的な正しさを証明したわけではない。人間が承認した期待値と根拠の対応が、現在も有効であることを機械的に確認しているだけである。実装が仕様に違反している場合は、正しいオラクルを無効にせず、実装側の問題として報告する。

## ファイル

各プロジェクトのルート直下にファイルを配置する。デフォルトは `test-gate-mvp`

```bash
## ファイルの配置
NAME=test-gate-mvp
cd /path/to/your-project
git clone --depth 1 https://github.com/ttomo-ttomo/test-gate-mvp.git "$NAME"
rm -rf "$NAME/.git"

## clone先のフォルダ名を変えた場合のみ
find "$NAME" -type f -exec sed -i "s#[t]est-gate-mvp\([^.]\)#$NAME\1#g" {} +

## プロジェクトのgit管理から外す場合
echo "$NAME/" >> .gitignore
```

README・各MD内のコマンド例や説明の `test-gate-mvp/` は、読み替えて使う（一括置換は任意）。

構成:

```text
test-gate-mvp/
├── README.md                # 全体像・実行手順
├── 01-human-review/         # 人間が編集・承認する表
│   ├── SPEC_INDEX.md        # 仕様の正本と実装/既存テストの対応
│   ├── OPEN_QUESTIONS.md    # 未規定事項の決定
│   └── TEST_RULES.md        # 承認した期待値・根拠
├── 02-short-term-test/      # 1〜2週間のテスト
│   ├── README.md            # 優先順位の考え方・入口
│   ├── WORKFLOW.md          # 実施手順
│   └── PROMPTS.md           # 工程別プロンプト5つ
└── 03-analyzer/             # Analyzer/Gate
    ├── README.md            # 使い方・HOLD対処
    ├── ANALYZER_AND_GATE.md # 判定モデル・制約
    ├── CLAUDE_PROMPTS.md    # Analyzer/Gate用プロンプト5つ
    ├── check.py             # Deterministic Analyzer + Gate
    └── tests/test_check.py  # 自動回帰テスト
```

## 1〜2週間で進める場合

優先順位・工程・手順・Claude向けプロンプトは [02-short-term-test/README.md](02-short-term-test/README.md) を参照。

**このリポジトリの担当範囲:** 上記はテスト活動全体の進行方針であり、現行の `test-gate-mvp` が5工程すべてを実装するという意味ではない。このMVPは、テストの期待値を確定する前に、仕様の根拠・承認・変更状況を `check.py` で決定的に点検する補助工程（上の全体像で△の2項目）を扱う。テスト生成・実行、カバレッジ、ミューテーション、欠陥注入は別途実施する。

## 人間とAIの分担

| 主担当 | 判断・作業 |
| --- | --- |
| 人間 | 仕様の正本・適用範囲、OPEN_QUESTIONSの決定、TEST_RULESの期待値と原文の対応を承認 |
| AI | 仕様/コードの探索、SPEC_INDEXやTEST_RULESのpending追加案、調査結果の説明 |
| check.py | 参照・SHA・承認状態・未決事項の決定的な確認 |

**仕様決定はOPEN_QUESTIONS.mdにだけ閉じ込めず、承認済みIssue/仕様/ADRの正本へ反映する。** `--stamp` はSHAを記録するだけで承認しない。

## 導入方針

1機能・1PRから始める。CI/新しいテスト生成器/外部LLM APIは導入しない。今あるテストランナーと併用できるが、このMVPではテスト実行結果を自動評価しない。仕様の曖昧さに気付けるか、根拠が古いときに保留できるか、人間の保守負荷が小さいかを確認する。
