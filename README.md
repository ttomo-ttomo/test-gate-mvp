# Test Gate MVP — 最小の Analyzer + Gate

> **対象:** 新しいプロジェクトにコピー可能な、Markdown中心の軽量運用。**これは導入設計とテンプレートであり、動作するAnalyzer/Gateの新実装ではない。** 現リポジトリの大規模な `test-evidence/` 実験を、他プロジェクトに丸ごと移植する必要はない。

## 目的

AIによるコーディング/テスト生成で、(1) **仕様とコード・既存テストの食い違いを早期に指摘する**（Minimal Consistency Analyzer）、(2) **根拠が不十分なテスト期待値をそのまま採用しない**（Minimal Oracle Gate）。人間の判断は仕様の正本・適用範囲と未決事項の決定に集中する。

### 何を削るか

既存の Evidence Index 103件、Oracle Registry 24件、147 finding のような大規模台帳、JSON/YAMLスキーマ、独立した自動推論エンジン、LLM API、Mutation Score、CI強制、専用テスト生成器、別エージェントによる毎回の監査は**必須にしない**。

## 最小ファイル構成

```text
test-gate-mvp/
├── README.md                # 導入と運用（このファイル）
├── SPEC_INDEX.md            # 仕様の正本・適用範囲・関連コード/テスト
├── OPEN_QUESTIONS.md        # 未決事項と決定・反映先
└── ANALYZER_AND_GATE.md     # AIに渡す検査手順と最小の判定基準
```

**実行可能な＋α:** 既存の `AGENTS.md` / `CLAUDE.md` に次の一文だけ追記する（既存ファイルがなければ作成は任意）。

> 変更・テスト生成の前に `test-gate-mvp/SPEC_INDEX.md` と `OPEN_QUESTIONS.md` を読み、`ANALYZER_AND_GATE.md` の判定基準で根拠と未決事項を確認する。判定不能な期待値は仕様適合テストとして確定しない。

CLI/自動化を後から足す場合も、最初は既存のgrep/テストランナーで十分。**本MVPの「Analyzer」と「Gate」はエージェントが実行する軽量な手順**であり、独立・決定的な自動検査器だと主張しない。

## 役割分担

| 作業 | AI | 人間 |
| --- | --- | --- |
| 仕様・Issue・ADR・コード・テストの所在を探す | 主担当 | 正本・優先順位の承認 |
| 機能と仕様/実装/テストの対応を提案 | 主担当 | あいまいな対応のみ確認 |
| 仕様と実装の相違・情報不足を列挙（Analyzer） | 主担当 | 仕様の解釈が必要な点の判断 |
| テスト期待値を仕様原文に照らして分類（Gate） | 根拠つき候補を提示 | 新たな仕様の承認・高リスクな期待値の判断 |
| テストコードを実装・実行 | 主担当 | 失敗原因・重要な仕様判断 |

人間が日常的に確認する主対象は **OPEN_QUESTIONS.md**。SPEC_INDEX.md は仕様改訂、正本変更、機能追加のときに見直す。ANALYZER_AND_GATE.md は初回合意後、原則そのまま。

## 1回の作業フロー（5ステップ）

1. **INDEX確認:** 対象機能の正規仕様、適用条件、実装、既存テストを特定。リンク切れ・出典不明は「未確認」。
2. **Analyzer:** 関連仕様とコード/既存テストを比べ、`一致 / 明確な矛盾 / 未規定 / 未検証` を短い表で報告。コードの現状を正しい仕様として使わない。
3. **Gate:** 追加する各assertionの期待値を、仕様の根拠で `採用可 / 保留 / 回帰記録のみ` に分類。構造上の疑いがなくても、意味的な支持が確認できなければ「保留」。
4. **人間判断:** 保留が仕様解釈に関係するならOPEN_QUESTIONS.mdに追加し、人間が決める。決定は**既存の正規仕様/Issue/ADRへ反映**し、質問票にだけ埋め込まない。
5. **テスト生成:** 採用可の期待値のみ仕様適合テストにする。保留は書かないか `todo`、回帰記録は仕様適合と明確に分離。差分と根拠をPR説明に記載。

作業中に重要な仕様上の矛盾を見つけたら、**実装を仕様へ合わせる前に確認が必要か**を判断する。仕様が確定していて安全な範囲ならテストに失敗を残せるが、未知の仕様を推測して直してはいけない。

## 判定の最小例

仕様: 「本文は最大2000文字。2001文字で400」。実装: `content.length > 2000`。

- ASCII/全角かなの2000・2001境界は、仕様に直接対応するので **Gate: 採用可**（対象と前提が一致する場合）。
- 絵文字1001個の受理/拒否は、文字数の単位が未定なので **Analyzer: 未規定 → Gate: 保留**。
- 既存実装が絵文字1001個を拒否するというテストは **回帰記録のみ**（仕様適合の証明にはしない）。
- 実装が2001文字を受理しているなら **Analyzer: 矛盾候補**。正当な期待値自体を否定してはいけない。

## チームへの導入方針

- 「品質ゲートを新設」ではなく「**AIに正しい仕様の場所を教え、未決事項を人間へ戻す**」として説明する。
- 最初は1機能・1PRだけで実験し、既存の開発プロセスを変えない。
- 追加される会議や承認は原則ゼロ。判断が必要なものだけ既存の仕様決定ルートに載せる。
- 成功指標はツールのfinding件数ではなく「**仕様の曖昧さを実装前に発見できたか**」「**根拠がない期待値が混入しなかったか**」「**更新負担が許容できるか**」。

## MVPの完了条件

- [ ] 最初の対象機能に正規仕様と関連コード/テストへの参照がある。
- [ ] 重要な未規定事項が質問票に残され、決定者/次アクションが明確。
- [ ] Analyzerの報告に仕様原文と実装参照、検査できなかった範囲がある。
- [ ] Gateで追加テスト期待値を1つ以上「採用可/保留/回帰のみ」に分類し、理由を示せる。
- [ ] 保留の期待値を仕様適合テストとして無断確定していない。
- [ ] 既存CIやソースを改変せず、小さなPRで運用できる。

詳しい設計思想は [../docs/evidence-based-test-generation/](../docs/evidence-based-test-generation/) にあるが、**このMVPの運用には読む必要がない**。

## Claude Codeへの指示プロンプト（コピーして使用）

以下をClaude Codeの作業開始時にそのまま渡してください。**このMVPのMarkdownに書かれた範囲だけを使い、既存の大規模なAnalyzer/Gateを新規導入・実装する指示ではありません。**

\`\`\`text
あなたはこのプロジェクトのAIコーディング・テスト支援担当です。
目的は、必要最小限のConsistency AnalyzerとOracle Validation Gateの考え方を用い、
仕様と実装の食い違いや、根拠のないテスト期待値の混入を防ぐことです。

最初に以下を読み、今回の対象機能を確認してください。
- test-gate-mvp/SPEC_INDEX.md
- test-gate-mvp/OPEN_QUESTIONS.md
- test-gate-mvp/ANALYZER_AND_GATE.md

作業手順：
1. SPEC_INDEX.mdを起点に、該当する仕様・Issue・ADRの原文、
   関連する実装・既存テストを調査してください。
   記載が古い、リンク先がない、正本が不明な場合は「未確認」と報告してください。
2. Minimal Consistency Analyzer：
   対象の仕様と実装・既存テストを照合し、
   「一致（確認範囲を明示）／矛盾候補／未規定／未検証」に分類してください。
   特に数値境界・単位・HTTP/API契約・認可・状態遷移を確認してください。
   各指摘には仕様の出典とコード/テストの場所を示してください。
3. Minimal Oracle Validation Gate：
   今回追加・変更するテストの各期待値について、
   (a) 正規仕様のどの箇所が根拠か
   (b) その根拠から適用条件を含めて期待値を導けるか
   (c) 未決事項や実装観測だけに依存していないか
   を確認してください。
   判定は「採用可／保留／回帰記録のみ」の3つです。
4. 未規定・根拠不足・資料間の競合がある場合は、
   OPEN_QUESTIONS.mdへの追記案（問い・根拠・選択肢・影響・判断担当）を提示してください。
   人間が決めていない仕様を補完しないでください。
5. 採用可の期待値だけを仕様適合テストとして使用してください。
   保留はassertionとして確定せず、回帰記録は仕様適合テストと区別してください。
   仕様の正本や人間の判断事項を無断で書き換えないでください。

重要な制約：
- 実装コードや既存テストを、仕様の正しさを示す根拠として扱わないこと。
- LLM自身の判断やテストPASSを、仕様適合の証明と呼ばないこと。
- 仕様・コードを確認できなかった部分を「一致」と報告しないこと。
- この作業のために新しいJSON台帳、Oracle Registry、専用Gate、
  外部LLM連携、CIチェックを追加しないこと。
- SPEC_INDEX.mdは、参照先の修正・追加が必要な場合に更新案を提示すること。
  OPEN_QUESTIONS.mdは人間の決定が必要な項目に集中すること。

最後に次の3つだけを簡潔に報告してください。
A. Analyzer結果：対象／仕様根拠／コード箇所／判定
B. Gate結果：テスト期待値／根拠／採用可・保留・回帰記録のみ
C. 人間への確認事項：未決の問い／選択肢／影響

対象範囲外の機能について網羅したと主張せず、
既存のチームの開発・レビュー手順をできる限り変えないでください。
