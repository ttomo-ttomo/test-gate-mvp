# Claude Code向け分割プロンプト — Test Gate MVP

長い一括指示を避けるため、**工程を5つに分ける**。番号順に1つずつClaude Codeへ渡す。各工程で結果を確認し、必要ならコミットしてから次へ進む。既存の完了済み工程は繰り返さず、差分だけ実施する。

**共通原則:** 人間が編集する正本はMarkdown表（SPEC_INDEX.md、OPEN_QUESTIONS.md、TEST_RULES.md）。AIは表の候補作成と実装を支援できるが、検査の実行結果は標準ライブラリPythonの決定的処理で出す。LLMによる毎回の合否判定を使わない。正規仕様の意味とテスト期待値の支持関係は、プログラムだけでは証明できないため承認者が確認する。

## Prompt 1 — 対象機能と仕様の所在

```text
今回は調査だけです。test-gate-mvp/README.mdとSPEC_INDEX.mdを読み、
対象機能を1つ選び、仕様/Issue/ADRの正本、実装、既存テストのリンクを調査してください。
SPEC_INDEX.mdに変更候補を反映してください。
OPEN_QUESTIONS.mdに「正本が不明」「仕様が曖昧」な点の追記案を作ってください。
勝手に仕様を決定せず、コードやテストを変更しないでください。

完了時は(1)確認した正規出典 (2)未確認箇所 (3)人間が決めることを短く報告。
```

**次へ進む条件:** 正規仕様と対象実装の参照が最低1組ある。資料の権威や適用範囲が不明なら先に確認する。

## Prompt 2 — 人間向けMarkdownルール表

```text
今回はTEST_RULES.mdの候補作成だけです。
SPEC_INDEX.mdで確認済みの対象機能について、仕様原文から検査したい期待値を最大3件抽出し、
TEST_RULES.mdの固定列にpendingで追加してください。
仕様アンカーは原文の正確な連続文字列、実装アンカーは存在確認できる文字列にしてください。
不明な値・決定のない条件はOPEN_QUESTIONS.mdに候補として整理し、承認済みにしないでください。
必要な場合はcheck.py --stamp <ID>でpending行の仕様SHAを記録してください。
既存の正規仕様/本番ソース/テストの書き換えはしないでください。

完了時は、追加した行の根拠、未決事項、承認者が確認する点だけを報告。
```

**次へ進む条件:** 人間が期待値と仕様の対応を確認し、対象行をapprovedにする。単なるSHA/アンカー一致は意味的な承認ではない。

## Prompt 3 — Deterministic Consistency Analyzer

```text
今回はAnalyzer部分だけを扱います。
test-gate-mvp/03-analyzer/check.pyを読み、TEST_RULES.mdから仕様/実装のファイルとアンカーを
決定的に検査できることを確認・必要なら最小修正してください。
仕様ファイルの変更と、実装アンカーの欠落/複数出現を区別して報告してください。
出典が読めない・解析できないときはUNVERIFIED/DRIFTとし、PASSにしないでください。
実装の原文アンカーの一致は実装動作の正しさを保証しないことを明示してください。
LLMの意味判定や外部サービス連携、新規JSON台帳は追加しないでください。

完了時は、実行コマンド・検査できた範囲・検査できない範囲を報告。
```

**次へ進む条件:** 同じファイル入力から同じAnalyzer出力が再現し、未知のパスやアンカー欠落を誤って正常扱いしない。

## Prompt 4 — Deterministic Oracle Validation Gate

```text
今回はGate部分だけを扱います。
check.pyのGate判定をTEST_RULES.mdの承認状態、仕様ファイルのSHA、
OPEN_QUESTIONS.mdの未決状態から決定的に導くよう確認してください。
approvedでも仕様SHAが失効または未決事項がOPENならHOLD。
pending/blockedもHOLD。正しい仕様への実装側DRIFTはオラクルのREJECT理由にしません。
仕様根拠の意味的な支持関係は承認者が確認したものだけを利用し、LLMに毎回再判定させないでください。
失効した承認を勝手に更新しないでください。

完了時はALLOW/HOLD一覧と理由、仕様の意味を証明していない限界を報告。
```

**次へ進む条件:** 承認・SHA・未決状態の各変更で同じ判定を返し、未承認をALLOWしない。

## Prompt 5 — 回帰テスト・運用確認

```text
今回は検証とREADME更新だけです。
python3 -m unittest discover -s test-gate-mvp/tests -v
python3 test-gate-mvp/03-analyzer/check.py
を実行してください。必要なら--strictも確認してください。

検証観点は、同一入力同一出力、未承認HOLD、仕様変更HOLD、未決事項HOLD、
実装アンカードリフトと仕様オラクルの判定分離、異常なMarkdownの拒否です。
テストが失敗したら無断で期待値を緩めず原因を修正してください。
READMEには実際に動くコマンドと人間が確認するポイントだけを書いてください。
既存の本番コード、仕様、テストは変更しないでください。

最後に変更ファイルとテスト結果、未検証の領域を示し、対象変更のみコミットしてください。
```

**完了の判断:** 単体テストPASSが確認でき、機械判定できない意味的な条件は人間のレビュー事項として残っている。

---

## 時間を節約する運用

- **新規導入:** 1 → 2 → 3 → 4 → 5
- **このリポジトリで既存のcheck.pyを使う:** 1 → 2 → 5（3・4は既存仕様の検証に限定）
- **仕様変更時:** 1 → 2（影響する行のみ、pendingへ）→ 5
- **ルール追加時:** 2 → 5

各工程を別セッションで実行する場合は、最後に確認したコミットSHAと未決事項のIDだけ次のセッションへ引き継ぐ。短いプロンプトでも仕様正本/承認状態を勝手に変更しない原則は維持する。
